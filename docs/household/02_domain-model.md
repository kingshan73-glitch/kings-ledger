# 02. 도메인 모델

엑셀의 6개 블록을 정규화한 개념 모델입니다. DB 설계(05)의 기반이 됩니다.

---

## 엔터티 관계 한눈에

```
인물(Person) ──┐
계좌(Account) ─┼─< 거래(Transaction) >── 카테고리(Category)
카테고리 ───────┘          │
                          ├─ 할부(Installment) ──< 할부 월분할 >
대출(Loan) ──< 상환(LoanPayment) >─┘
```

핵심은 **거래(Transaction) 한 테이블**이 엑셀의 수입·지출·이체·납부를 모두 담고, **유형(type)** 으로 구분하는 것.

---

## 1) 거래 (Transaction) — 중심 엔터티

엑셀 블록 02·03·04·05·06을 통합한 단일 테이블. `type`으로 성격을 구분한다.

| 유형(type) | 의미 | 엑셀 블록 | 금액 부호 | 잔액 영향 |
|-----------|------|-----------|-----------|-----------|
| `income` | 수입 | 02 | + | 입금계좌 +금액 |
| `expense` | 일시불 지출 | 06 | − | 결제수단(현금/카드) |
| `installment` | 할부 지출 | 05 | − | (월분할로 반영) |
| `transfer` | 통장 이동 | 03 | 0 | 출금계좌 −, 입금계좌 + |
| `payment` | 카드·대출 납부 | 04 | − | 출금계좌 −금액 |

**공통 필드**
- 날짜(date), 유형(type), 금액(amount), 항목/카테고리(category FK)
- 내역(memo·상세설명), 비고(note)
- 거래처/입금처(counterparty) — 수입의 입금처, 지출의 가맹점명
- 결제수단(payment_method) — 현금·카드 등 (지출용)
- 계좌(account FK) — 입금계좌 / 출금계좌 (유형에 따라 의미)
- 이체용: from_account / to_account
- 용돈 귀속 인물(person FK, nullable)
- 할부 FK(installment, nullable — 할부 회차가 이 거래로 반영될 때)

## 2) 계좌 (Account)

엑셀 02번 "은행통장" 표. 잔액 관리의 단위.
- 필드: 계좌명(`토스뱅크`, `국민은행-한`), 은행, 계좌번호(마스킹), 명의(인물), 종류(입출금/주식/가족), 활성여부, 표시순서, 기초잔액
- **현잔액 = 기초잔액 + Σ(입금) − Σ(출금)** — 거래에서 자동 계산(저장하지 않음).
- ⚠️ 로그인 ID/비밀번호는 **필드로 두지 않는다.**

## 3) 카테고리 (Category)

지출/수입 분류. 엑셀의 18개 지출 카테고리 + 수입 분류.
- 필드: 이름, 종류(수입/지출), 표시순서, 활성여부, (선택)고정비 여부
- 지출: 외식비·식료품비·생필품·양육비·육아용품·적금·보험·기부금·교통비·차량유지비·통신비·관리비·의료비·쇼핑·경조사비·레저/기타·용돈·할부
- 수입: 급여·이자·환급/캐시백·기타 등 (원본 "항목"에서 도출)

## 4) 결제수단 (PaymentMethod)

현금 + 카드들. 카드는 명의(인물)와 연결.
- 필드: 이름(`삼성카드(한)`), 종류(현금/체크/신용/할부), 명의(인물), 연결계좌(결제 출금계좌), 활성여부
- "지불방식 별 지출 합계"(현황 01)의 집계 기준.

## 5) 인물 (Person)

용돈·카드 명의 귀속 대상.
- 필드: 이름(김하늘·이바다·가족), 표시순서
- 용돈/외식비 사용 현황(현황 01) 집계의 기준.

## 6) 할부 (Installment)

엑셀 05번 블록. 한 번 등록하면 매월 자동 분할 반영되는 스케줄.
- 필드: 시작일, 사용카드(결제수단 FK), 카테고리 FK, 내용, **총금액**, **총 회차**, 월 금액(=총금액/회차), 시작회차
- 파생: 현재 회차, 남은 잔액 = 총금액 − (지난 회차 × 월금액)
- 매월 해당 월금액이 `installment` 유형 거래로 집계에 들어간다.

## 7) 대출 (Loan)

엑셀 01번 현황의 대출표.
- 필드: 대출명, 발생일, 대출금액(원금), 현재잔액, 만기일, 이자율, 월납입금, 상태(상환중/완료)
- 연결: 상환 거래(`payment`)와 매칭 → 잔액 자동 감소.

## 8) 대출 상환 (LoanPayment) *(거래의 하위 뷰)*

`payment` 유형 거래 중 대출에 연결된 것. 별도 테이블 없이 거래의 loan FK로 표현 가능.
- 회차별 원금/이자 분해는 2차 고도화 항목.

## 10) 정기지출 / 자동이체 (ScheduledPayment) ★

매월(또는 매주) **정해진 날에 나갈 돈** — 현금흐름 예측의 핵심 입력.
기존 `recurring-expenses` 패턴 재활용 가능.
- 필드: 이름, 종류(자동이체/구독/보험/통신/관리비/적금/대출상환/카드대금 등), 금액(고정 또는 추정), 주기(매월/매주/격월), **납부일**(일/요일), 출금계좌 FK, 카테고리 FK, 명의(인물 FK), 활성여부, 시작/종료일
- 예측 소스가 되는 세 갈래:
  - 명시적 정기지출(이 테이블): 보험·통신·관리비·적금·구독 등
  - **대출 월납입금**(Loan): 약정일 + 월납입금
  - **할부 월금액**(Installment): 진행 중 회차
  - **카드대금**(추정): 미결제 카드지출 누적 → 결제일·금액 추정

## 9) 거래 수집함 (Transaction Inbox — staging) ★

수입·지출의 **약 95%를 자동 수집**해, 사람이 한 번 점검한 뒤 확정하기 위한 임시 보관 단계.
자동 수집 건은 본 거래(Transaction)에 바로 들어가지 않고 여기서 **검토 대기** 상태로 머문다.
- 필드: 원문(raw text/출처), 수집일시, 추정 날짜·금액·가맹점, **추정 카테고리/계좌/결제수단(자동분류)**, 신뢰도, 상태
- **상태(status):** `pending`(검토대기) → `confirmed`(확정·거래로 전환) / `ignored`(제외) / `duplicate`(중복)
- 확정 시 → `hh_transaction` 한 건 생성(또는 수집함 레코드에 status만 두고 거래로 승격).
- 중복 방지 키: (날짜 + 금액 + 가맹점 + 출처) 해시.

> 설계 선택지 — (A) 별도 `hh_transaction_inbox` 테이블 + 확정 시 `hh_transaction`으로 복사,
> (B) `hh_transaction`에 `status` 컬럼 하나로 통합(pending/confirmed). DB 설계(05)에서 확정.

---

## 메뉴 ↔ 엔터티 매핑

| 메뉴 | 사용 엔터티 |
|------|------------|
| 수입 | Transaction(`income`) + Category(수입) + Account |
| 지출 | Transaction(`expense`,`installment`) + Category(지출) + PaymentMethod + Installment |
| 현금관리 | Account(잔액) + Transaction(`transfer`) + 모든 거래의 잔액 반영 + **현금흐름 예측 요약** |
| 대출관리 | Loan + Transaction(`payment`, loan 연결) |
| 통계 | 위 전체의 집계(월별 추이·카테고리 비중·수지) + **현금흐름 예측/자금 스케줄(ScheduledPayment+Loan+Installment+카드대금)** |
